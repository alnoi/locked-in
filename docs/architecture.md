# Архитектура

Один репозиторий: apple/ — SwiftUI-клиент; backend/ — Go-сервис; docs/ — решения.
Apple-клиент подключён к API; также имеет отдельный локальный режим без сервера.

## Бэкенд

Модульный монолит. Сейчас два предметных контекста: identity и tracker.
Tracker объединяет доски, списки, задачи, теги и комментарии; календарь — выборка задач.

- models/ — сущности, входы/выходы, фильтры и простая валидация.
- domain/ — чистые правила вложенности, наследования списков и применения изменений.
- usecase/ — сценарии, транзакции и узкие интерфейсы хранилищ.
- usecase/tracker_authorized.go — обязательная проверка пользователя и передача owner scope.
- repository/postgres/<entity>/ — SQL, строки БД и мапперы для каждой сущности.
- transport/http/local/ — HTTP, преобразование моделей и сгенерированных DTO.
- internal/app/ — сборка зависимостей, миграции, HTTP-сервер и остановка.
- pkg/transaction_manager/ — pgx-транзакция через context; репозитории не управляют транзакциями.

Контракт API: backend/api/service/local_tracker/openapi.yaml.
Серверные интерфейсы, DTO и Go-клиент генерируются oapi-codegen; generated/ вручную не редактируется.
PostgreSQL-схема версионируется миграциями Goose.

## Целостность

Каждая сущность ограничена owner_id. Межсущностные FK включают owner_id.
Изменения данных одного пользователя сериализуются транзакционной advisory-блокировкой PostgreSQL.
Проверка графов и запись выполняются в одной транзакции, чтобы не появлялись циклы и удалённые ссылки.
Разные пользователи не блокируют друг друга. Ошибки API не раскрывают SQL и внутренние детали.

## Локальный режим

Пользователь создаётся по бизнес-ключу username при первом запуске, ID выдаёт БД.
Регистрации и аутентификации пока нет: сервер слушает только loopback и отклоняет browser Origin.
Перед доступом с iPhone или публикацией понадобится отдельный этап аутентификации.
Apple-клиент обновляет серверные данные при запуске/активации, вручную и каждые 30 секунд; при офлайне или очереди — каждые 5 секунд.
В серверном режиме OfflineTaskRepository атомарно хранит snapshot и очередь изменений задач отдельно для каждого адреса. Создание, правки, завершение и удаление доступны офлайн; коллекции и комментарии пока требуют связи. Красный флажок означает сохранение на устройстве без подтверждения сервера.
Созданная офлайн задача сохраняет UUID: POST с тем же id не создаёт дубль и не перезаписывает существующую запись. Версия очереди не позволяет старому ответу подтвердить более свежую правку. При синхронизации неизменённые локально поля берутся с сервера; при конфликте одного поля локальная правка приоритетна. Ошибки валидации оставляют задачу в очереди с предупреждением.
Архив локального режима не смешивается с серверной очередью. Смена пользователя на сервере при наличии очереди блокирует её отправку.

## Проверки

Unit-тесты проверяют чистые правила. HTTP-тесты используют настоящую PostgreSQL и отдельные временные схемы.
Проверены владельцы, наследование фильтров, глубина, конкурентные изменения, календарь, сохранение и миграции Up/Down.
